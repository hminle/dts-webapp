Taking DTS Analysis public

The Daily Treasury Statement app leaves the laptop. A job builds the data once a day, Cloudflare stores it, and Vercel serves a website that only reads it.

8 phases (0 done) 20 read routes, all GET 9 Treasury tables + 1 derived Hosting: Vercel Hobby + Cloudflare R2
Part 1

The plain picture

What the plan builds and why, for anyone.

What exists today

One laptop
Website
Program
Database file
Fetch button

The app runs on one computer. Someone presses Fetch to pull new Treasury numbers, and the same program writes the database while it answers questions about it.

What breaks when strangers use it

✕ Reading while a fetch is writing can crash the program.
✕ A fetch that fails halfway can leave a table empty.
✕ Most questions are sent in a form no web cache will store, so every visitor makes the server work.

Fine for one person. With many visitors, each problem gets worse.

The idea in one picture

Split writing from reading. A job builds a fresh, checked file once a day. The website never writes, so nothing can collide.

GitHub runs the daily job. Cloudflare keeps today's file and a copy of every earlier day. Vercel rebuilds the website with the new file baked in.

    Part 3

    Developer briefing

    For someone who has not opened the plan files. Paths are relative to the repo; REF is dts-analysis/fullstack_app, FAM is family-financial-app.

    Goal

    Rebuild REF as a public, free, read-only web app. Copy FAM's repo layout (backend/ uv + FastAPI, frontend/ pnpm + Vite + TanStack + shadcn base-nova), its tokens and its inset sidebar. Port REF's financial logic, folding in the fixes from REF's own improvement plan. Accounts and payments are a later plan.

    One business day, in order

    1. Actions 22:30 UTCcf r2 objects get latest/… into backend/data/
    2. app.ingestCopy to *.building.duckdb; fetch rows after each table's MAX(record_date); any Treasury error aborts the run
    3. app.ingestRecompute daily_net_transfers for touched fiscal years (DENSE_RANK day numbers); write metadata; validate; CHECKPOINT; os.replace
    4. ActionsIf changed=true: put snapshots/DATE/, then latest/, then POST the Vercel Deploy Hook
    5. Vercel buildfetch_artifact downloads and opens the file; a bad file fails the build and the old deployment stays live
    6. On failurehealthchecks.io /fail ping emails you; R2 and the site keep yesterday's data

    API surface: every route becomes GET

    REF sent most analysis queries as POST with a JSON body. No CDN caches POST, so bodies become query parameters. Shapes stay byte-compatible with REF, so the ported pages work unchanged.

    Key decisions

    • Remove the concurrency problem instead of fixing it.REF's improvement phases 1–2 (cursor discipline, fetch locks, task keys) become unnecessary; 3–7 fold into Phases 2, 3, 5 and 6 here.
    • Ingestion is all-or-nothing.REF caught per-endpoint errors and its client returned partial pages on failure. Here any error aborts and validation refuses a file that shrank, so a truncated artifact is never published.
    • Deploy is the data refresh.The file ships inside the function. Rolling back data means promoting yesterday's deployment. No runtime download, no sync code.
    • Handlers are sync def.REF's async def handlers blocked the event loop on DuckDB calls. Sync handlers run in FastAPI's threadpool, each with its own cursor.
    • Cloudflare stores, Vercel serves.No Cloudflare proxy in front of Vercel and no domain yet. All Cloudflare work uses the cf CLI (cf@1.0.0-beta.18), which authenticates with CLOUDFLARE_API_TOKEN in CI.
    • The bucket is public-read.The data is public domain, and the Python build can then download with stdlib only. Revisit with signed URLs when paid tiers arrive.
